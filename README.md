# Zvid custom app for Make.com

Custom app definition for [Zvid](https://zvid.io) on the [Make developer platform](https://developers.make.com/custom-apps-documentation): render videos/images from JSON or templates and react to render events with an instant trigger.

## Components

| Component | Type | What it does |
| --- | --- | --- |
| `modules/get-project-schema`, `list-supported-elements`, `get-element-docs`, `get-example-project` | AI Authoring | Retrieve the live plan-aware schema, professional guidelines, supported fields, and validated starting projects for an attached AI module |
| `modules/repair-project` | AI Authoring | Conservatively repair generated JSON and return changes, remaining errors, and professional layout warnings |
| `connections/zvid-api-key` | Basic (API key) connection | Stores the `zvid_…` key, validates it against `GET /api/user/profile`, shows the account email |
| `general/base.iml.json` | Base | `https://api.zvid.io` + `x-api-key` header on every request, sanitized logs, shared error mapping |
| `modules/create-render` | Action | `POST /api/render[/image]/api-key` from a project JSON or template + variables, with output overrides and optional per-job webhook |
| `modules/validate-render` | Action | `POST /api/render/validate/api-key` — pre-flight check of a payload/template against the real backend validation (free, no render). Outputs `valid`, field-level `errors` and your `planLimits` instead of failing the scenario, so you can branch with a router |
| `modules/get-render` | Action | `GET /api/jobs/{jobId}` — state, output URL, thumbnail, failure reason |
| `modules/list-renders` | Search | `GET /api/jobs`, iterates `body.jobs`, optional type filter |
| `modules/list-templates`, `get-template` | Search/Action | Browse owned templates and retrieve complete project JSON before editing |
| `modules/create-template`, `update-template`, `delete-template`, `duplicate-template` | Actions | Create validated reusable templates, update them, archive them, or make editable copies |
| `modules/preview-template`, `render-from-template` | Actions | Free variable-resolution dry run, then render after preview passes |
| `modules/watch-renders` + `webhooks/render-events` | Instant trigger | Registers a Zvid webhook on activation (`attach` stores the returned `webhook.id` and signing `secret`), deletes it on deactivation, and emits `render.completed` / `render.failed` events |

## Importing into Make

Make apps are hosted on their platform; these files follow the layout used by the official **Make Apps Editor** VS Code extension (`integromat/vscode-apps-sdk`):

1. Install the extension and sign in with a Make API token (Custom Apps scopes).
2. Create a new app named **Zvid** (label; version 1) from the extension, then **Clone to Local Folder** to get a workspace with `makecomapp.json` (the manifest with your app's `origins` is generated by the extension — it is intentionally not committed here).
3. Copy the contents of `src/zvid/` over the cloned skeleton, matching component names (`general/base`, connection `zvid-api-key`, webhook `render-events`, and the module folders).
4. Right-click `makecomapp.json` → **Deploy to Make** (or deploy per component).
5. In the Make web UI, add module labels/descriptions, upload an icon, and test each module in a scenario.

Alternatively, paste each JSON block into the matching tab of the web-based app editor (Base, Connection → Parameters/Communication, each Module → Communication/Mappable parameters/Interface, Webhook → Attach/Detach/Communication).

## Validate-before-render pattern

For AI-generated projects, retrieve the schema, closest example, and relevant element docs before asking the model to compose JSON. Treat validation errors and layout warnings as fix-before-render feedback.

The AI Authoring modules provide that context directly from the authenticated, plan-aware backend; MCP is optional for Make scenarios.

For a reusable template, run the authoring/validation loop, then **Create a Template**. The lifecycle is list/get → update or duplicate → preview with variables → render. **Delete a Template** archives it and should only be used for an explicit removal request.

For scenarios where the project JSON is mapped from earlier modules (or generated by an AI module), insert **Validate a Render Payload** before **Create a Render** and route on the boolean `valid` output:

- `valid = true` → proceed to Create a Render (the `creditsRequired` output tells you the cost up front; `payload` is the resolved project with defaults applied).
- `valid = false` → the `errors[]` array carries field-level problems (`{field: "visuals[0].src", message: …}`) and `planLimits` echoes your plan's actual ceilings — feed both back to the AI module or into an error notification.

The module returns a bundle either way (HTTP 400 from the API is mapped, not thrown), so invalid payloads never kill the scenario run. Validation runs the same backend pipeline as render submission — template resolution, plan limits, full project schema — and costs no credits. For authoring guidance (JSON Schema, per-element docs, examples), see the [`zvid-schema`](../schema) package and the [zvid-mcp](../mcp) server; the backend validation always wins over other docs.

## Webhook signature note

Zvid signs deliveries with HMAC-SHA256: `X-Zvid-Signature: sha256=hex(hmac(secret, "<X-Zvid-Timestamp>.<raw body>"))`. The webhook `communication.iml.json` includes a best-effort `condition` re-computing the signature with the secret captured at attach time. IML re-serializes the parsed body (`json(body)`), which matches Zvid's compact `JSON.stringify` output; if your Make zone rejects the `sha256(…, 'hex', key)` HMAC form, remove the `condition` line — Make webhook URLs are unguessable, which is the default security model for Make apps, and the attach/detach lifecycle still limits exposure.
